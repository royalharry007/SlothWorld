# Deploying SlothWorld on Render

This deploys one Docker web service. It serves the 3D app and the API, and runs **Ollama with `gemma3:1b` on CPU** inside the same container, so visitors can create worlds from their own PDFs.

## What visitors get

- **Sample world:** instant, the same as running locally.
- **PDF → world:** generated by `gemma3:1b` on the server's CPU. It takes about **3–6 minutes** for a 4-island world. The progress screen says so and keeps the connection alive.
- **Privacy wording switches automatically:** in hosted mode the UI says PDFs are processed in memory on the SlothWorld server, aren't stored and aren't sent to any AI company. It no longer claims "your PDF never leaves this computer".
- **Rate limit:** 3 new worlds per visitor IP per hour (`SLOTH_RATE_LIMIT_PER_HOUR`). Only one generation runs at a time; others get a "busy, try again shortly" message.

## Steps

1. Push this repository to GitHub. `render.yaml`, `Dockerfile` and `docker/start.sh` are already in it.
2. In the Render dashboard choose **New → Blueprint** and pick the repository. Render reads `render.yaml` and creates the `slothworld` web service.
3. Confirm the plan (default **Pro**: 2 CPU / 4 GB) and deploy. The first build pulls the Ollama image and bakes the 815 MB model into it, so expect around 10–15 minutes.
4. When the deploy is live, open the service URL. The landing page dot should be green and read *gemma3:1b … running on this SlothWorld server*.

`autoDeploy` is off, so pushing new commits won't trigger paid rebuilds. Use **Manual Deploy** when you want an update.

## Settings

All are set in the `Dockerfile`; you can override them in Render → Environment.

| Variable | Container default | Meaning |
|---|---|---|
| `SLOTH_MODEL` | `gemma3:1b` | Model baked into the image (change the Docker build arg too) |
| `SLOTH_NUM_THREAD` | `2` | CPU threads; match the plan's CPUs |
| `SLOTH_MAX_CONCEPTS` | `4` | Islands per world (2–6); fewer is faster |
| `SLOTH_NUM_CTX` | `4096` | Model context window |
| `SLOTH_CALL_TIMEOUT_MS` | `600000` | Per model call |
| `SLOTH_RATE_LIMIT_PER_HOUR` | `3` | New worlds per visitor per hour (0 = unlimited) |
| `SLOTH_TUTOR_LIMIT_PER_HOUR` | `40` | Questions to Pip and Hoot per visitor per hour (0 = unlimited) |
| `SLOTH_HOSTED` | `1` | Hosted privacy wording, trusts Render's proxy for visitor IPs |
| `SLOTH_NUM_GPU` | `0` | CPU only |

## What was tested locally

Docker isn't installed on the development machine, so **the image itself hasn't been built yet**. The first Render build is its first real build. Everything inside it was tested by running the server with the container's exact settings (`e2e/hosted.ts`, all 5 checks passed):

- health reports hosted mode, the model and the rate limit;
- hosted privacy wording appears and the local-only claim is gone;
- a full PDF → world generation through the browser with **gemma3:1b on 2 CPU threads, no GPU**: 4 islands and 11 stations in 4 min 32 s, with keep-alive pings handled;
- a second upload in the same hour is rate-limited with a clear message;
- no page errors.

If the Render build fails, the build log will show which step. The most likely spots are the Ollama base image tag and copying the Node binary between images.

## About quality with gemma3:1b

The 1B model is much weaker than Gemma 4 E2B. In testing it often marked the **wrong** quiz answer as correct. SlothWorld now checks every quiz's answer key against the cited PDF passage *and* against the model's own explanation, and drops any quiz where they disagree, with a note in the validation report. In tests this dropped all 5 wrong keys from gemma3:1b and none of the 10 correct Gemma 4 quizzes.

Claim checks from the 1B model are simpler and can occasionally be mislabelled; the source passage is always shown after answering. For the best quality, run locally with `gemma4:e2b-it-qat` (the default). Use the Render deployment for public access.

`gemma3:1b` is an open-weight model under the **Gemma Terms of Use**. `gemma4:e2b-it-qat` is reported by Ollama as **Apache 2.0**.
